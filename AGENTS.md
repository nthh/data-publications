# Dataset publication instructions

- Keep one canonical record per ID: discovery-only records live at `candidates/<id>/dataset.yaml`; selected build, preparation, and history workspaces live at `datasets/<id>/dataset.yaml`. Generate repository-wide indexes from both roots; do not add a separate manually maintained records/products inventory. Promote with `git mv candidates/<id> datasets/<id>` before adding conversion or preparation files; never copy a record.
- Preserve producer identity, source pins, units, nulls, uncertainty, geometry/grid and record multiplicity. Keep display derivatives separate from analytic data.
- Record validation criteria before evaluating new results. Preserve failed historical checks; record justified follow-up diagnostics separately.
- Keep bulk data, raw GEE captures, environments and credentials in ignored local storage. Publish only explicit source inventories and reviewed artifacts.
- Default to offline checks. Live GEE requests, exports, costly compute and publication need explicit authorization for the task. Existing authorization persists within that task.
- Use focused tests and a clean-checkout rehearsal after changing runtime paths or build inputs. Never overwrite an immutable release.
- Commit work locally. Push, create remote repositories, upload data or submit registries only when explicitly requested.
- Source code is Apache-2.0; dataset-specific licenses remain separately declared in dataset.yaml and release metadata.

## Generated publication catalog

- `candidates/` and `datasets/` together contain the only editable dataset records, with exactly one canonical record per ID. Export catalog-input snapshots from an immutable release; never hand-edit a snapshot or duplicate dataset facts in another inventory.
- `catalog/` is generated by `scripts/publication_catalog.py write`. Never edit generated STAC or consumer documentation directly. Run `scripts/publication_catalog.py check` before committing.
- Only published records with checksum-bound metadata, real HTTPS package URLs and matching hosting evidence enter `catalog/`. Zero collections is a valid initial root, not a publication readiness claim.
- Use the locked standalone Rashid gate under `tools/portolan`; keep conversion environments separately pinned. Preserve incomplete stac-check advisory results as incomplete.
- The publication path is `scripts/publication_catalog.py stage` followed by a separately authorized upload of its exact plan. Do not mix this generated tree with `portolan push` or another metadata-rewriting publisher.
- Update `catalog.publish.yaml` only with confirmed destinations and public navigation URLs. Never put credentials in it. Staging still requires published records and matching evidence from real hosted checks, even when the destination is configured.
- Consult the Portolan skills and specification revisions recorded in `tools/portolan/pins.json` when changing the catalog workflow. See `docs/catalog-workflow.md` for the contract and remaining publication gates.

## Candidate discovery

- Keep cross-catalog observations in the canonical record's optional `discovery` object. Reference immutable research observations by path, SHA-256 and key; preserve the frozen community audit.
- Match scientific product, edition and scope before reusing an ID. A shared citation, name, catalog counterpart or world-sized bbox alone is insufficient. Regional and global products may need separate records.
- `CANDIDATES.md`, `candidates.csv`, and `SHORTLIST.md` are generated by `scripts/catalog.py --write`; check them with `--check`. Discovery records stay public under `candidates/`. Existing native access is a reuse lead, not proof of a complete validated copy or redistribution permission.
- Discovery capture is metadata-only and opt-in. Use a new destination for a new capture. No dataset downloads, live GEE jobs, uploads or visibility changes are implied by candidate review.
