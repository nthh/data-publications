# Publishing and checking Source Cooperative releases

This directory executes a reviewed upload plan and checks the hosted results. Dataset conversions remain in their dataset projects; an upload does not change analytical or display bytes.

## Environment and authentication

```sh
uv sync --locked --project scripts/source_publish --no-build
uv run --locked --project scripts/source_publish python -m pytest tests/test_source_upload.py tests/test_source_api.py tests/test_hosted_validation.py tests/test_browser_range_evidence.py tests/test_hosted_ndjson.py tests/test_hosted_catalog_scope.py tests/test_bounded_http.py tests/test_query_hints.py tests/test_hosted_viewer.py
```

Use the official Source Cooperative CLI 0.3.0 for login and the S3 credential process. For long transfers, sign in with `source-coop login --scope "openid offline_access"` so the CLI can refresh access during the run. Pass its absolute executable path to the uploader's `--credential-helper`. Credentials stay in the existing OS credential store and process memory; never save or print credential-helper output in release evidence. This workflow does not use permanent access keys.

## Prepare a release

1. Keep one canonical record per ID: discovery-only records may remain at `candidates/<id>/dataset.yaml`, but move a selected record with `git mv candidates/<id> datasets/<id>` before product preparation or publication. Published records must be under `datasets/<id>/dataset.yaml`. Preserve immutable analytical packages and separate pinned display packages.
2. Generate product documentation with `scripts/source_products.py write` and verify it with `check`.
3. Confirm the owner and create one Source product for each dataset. During the November 2026 publication, the deployed product-creation API returned HTTP 501, so creation used the signed-in web form. Retain sanitized creation receipts with exact owner, product ID, storage connection and initial visibility.
4. Use `scripts/source_products.py stage` with explicit `--package ID=PATH` and `--display-package ID=PATH` mappings and a new output directory. Stage rehashes every local file. Review the exact object keys, byte counts, hashes and content types, then commit the plan and its SHA-256 before execution.
5. Freeze analytical query IDs and browser cases before evaluating hosted results. A staging result does not prove that upload or hosting has succeeded.

Current selected products belong to `nthh`. They contain GeoParquet, PMTiles and their versioned evidence. The aggregate catalog remains Git-backed and can be served separately through GitHub Pages; a sixth Source product is unnecessary.

## Execute the exact plan

`upload.py` defaults to a dry run. Select a single `--dataset`, the exact `--plan`, an absolute `--data-root`, the repository root and explicit package mappings. Execute only with `--execute`, `--credential-helper` and `--expected-plan-sha256`. Use a new `--output` directory for every attempt. `--include-readme` also selects that product's generated mutable root README.

The executor checks all selected local hashes before writes, refuses differing immutable remote objects, uses conditional writes, and reads complete remote bytes back to verify SHA-256. It checks remote content type as well as size. Existing matching objects are verified before being skipped. Multipart uploads use bounded parts and journal their IDs and completed parts. Interrupted attempts retain their receipts; scoped recovery accepts only incomplete multipart IDs from a matching prior plan via `--recover-multipart`.

A stopped failed attempt can be resumed with `--resume-from PRIOR_RECEIPT` into a new output directory. Reuse is limited to immutable objects whose prior full remote readback matched the exact plan, size and SHA-256. Each reused object gets a current HTTP 200 HEAD check for size and content type, plus checksum bindings to the original summary and object receipt. This is explicitly prior full-readback evidence with a current HEAD check; it is not a fresh full-object hash. Mutable READMEs are checked normally. If the earlier attempt left an incomplete multipart upload, either recover that exact upload with `--recover-multipart` and pass its successful `--recovery-receipt`, or use the explicit same-ID replay described below. An attempted abort is not proof that cleanup succeeded. Keep the original receipt files unchanged so the evidence chain can be checked.

To complete the original interrupted multipart upload, combine `--resume-from PRIOR_RECEIPT` with `--resume-multipart`, `--expected-resume-summary-sha256` and `--expected-resume-record-sha256`. Freeze those digests and the exact plan before execution. This mode accepts exactly one failed large immutable object and takes its upload ID only from the checksum-bound journal. It refuses a target that already exists, freshly hashes the entire local file, uploads every part again from part 1 with that same ID, and completes conditionally with `IfNoneMatch=*`. It does not create a replacement upload or rely on old part ETags. Final HEAD size/type and a fresh full remote SHA-256 must pass. The summary records `resume_mode: existing_multipart`; old failed aborts remain failed historical evidence.

During same-ID replay, an `UploadPart` `ExpiredToken` response or a typed local credential-expiry check can retry the exact same part bytes with a fresh helper/client. This is limited to two retries per part and 90 seconds of cumulative expiry waiting, in steps of at most five seconds. No other operation or error is retried by this rule. The receipt records the retry reason and time without credentials; part ETags and byte counts advance only after a successful response. The frozen authentication-retry contract and the earlier failed attempt remain separate evidence.

A replay error leaves the upload ID and current part journal intact. It never silently starts another upload or declares cleanup complete. If the target completes and a later small object fails, this original same-ID mode will refuse the now-present target on retry; an ordinary exact-plan execution can instead verify existing objects by full remote readback. The frozen November GRWL protocol and Source abort diagnosis are retained under `research/source-publication-20261106/`.

Never infer success from an exit code alone: retain the completed per-object receipts and summary, including failures from earlier attempts. The plan deliberately excludes raw source archives, raw GEE captures, credentials and local environments.

After verified hosting is recorded in the canonical records, regenerate the consumer READMEs and stage a new plan. Use `upload.py --readme-only` with that exact plan SHA and a new receipt directory to update each product’s mutable root README. This mode verifies the planned README and uses a conditional write; it does not select or retransmit immutable data. Do not combine it with `--include-readme` or multipart recovery. Preserve the original immutable upload plan and receipts.

## Validate actual hosted behavior

`validate_hosted.py` consumes the exact plan, upload receipts and frozen query controls. It checks anonymous actual range bytes, content types, CORS, metadata and links, and compares local versus remote analytical subsets including duplicate multiplicity, values and geometry. Full-object checksum evidence comes from the uploader's actual remote readback; current HTTP range checks are a separate observation. Neither implies scientific accuracy or strict equality to GEE.

Metadata checks validate declared JSON Lines audit files record by record, including empty files and blank lines, while ordinary JSON remains a single document. All planned metadata retains its byte/hash/MIME checks. Catalog-link validation starts from current analytical catalogs and collections plus styles declared by the checksum-bound display manifest. It follows reachable references and requires every current style to point to its manifest-pinned PMTiles. Archived snapshots retain their historical paths and are not active consumer styles unless the current catalog links to them. External producer archives with the sole `source` role and explicit provenance/license links remain references; their transport is outside this hosted-product check. External analytical, structural and display links are rejected.

`prepare_query_hints.py` reproducibly exports the supplement from local releases. Pass the original plan and controls with their SHA-256 values, one absolute `--package DATASET=ROOT` mapping for each controlled dataset, and a new `--output` path. It rehashes every Parquet, validates its GeoParquet covering metadata and selected WKB envelopes, and derives the centers and row-group estimates without network access. The November follow-up regenerated the frozen supplement byte for byte; its reproduction receipt is retained with the publication evidence.

For a spatial-query follow-up, supply `--query-spatial-hints` and its explicit `--query-spatial-hints-sha256`. The supplement binds the original query controls and planned Parquet hashes. The validator checks each unchanged local covering bbox, retains unfiltered ID multiplicities and footer counts, and compares all columns for exactly the same selected rows. DuckDB then reads Source through an anonymous forwarding proxy that permits only planned Parquet URLs and bounded ranges (64 MiB per request, 128 MiB total per asset). Its request ledger distinguishes local row-group byte estimates from actual received bytes. No local data are substituted for remote responses. If a resumed uploader receipt reuses original checksum proofs, supply each original failed receipt through `--prior-receipt`; the validator verifies the exact original summary and record bytes rather than accepting a copied checksum claim. For same-ID multipart replay, retain the original failed target record as well as the previously verified records. The validator also binds that failed record and original upload ID to the newly completed target, which must have a fresh full remote readback. Pass the independently frozen original digests through both `--expected-multipart-parent-summary-sha256` and `--expected-multipart-parent-record-sha256`; the validator requires them for this mode and records the verified parent hashes in its evidence.

Frozen IDs are queried separately with exact equality while preserving the complete combined result multiset and global multiplicity checks. ID parameters use their exact decimal/string representation: with GRWL’s uint64 IDs, binding a Python integer makes DuckDB cast the column to HUGEINT and defeats min/max pruning. Regression fixtures also preserve numeric IDs and distinct string IDs such as `001` and `1`. The request, byte and 1,000-row comparison limits are unchanged.

`prepare_hosted_viewer.py` binds the local UI to exact Source URLs and prepares fixed browser cases. Its loopback server serves only UI files and configuration; dataset bytes come from Source. `scripts/cloud_viewer/hosted-browser-check.mjs` records real Chrome requests, render results and screenshots. A pilot checks only its selected dataset; other products remain untested until their cases run. The complete run includes both LakeATLAS layers and GRWL width views from zoom 0 through 12.

Browser requests normally have a 16 MiB per-request limit, with 128 MiB per case and 1 GiB per run. GRWL's verified Parquet has a 19,783,655-byte metadata footer. The retained failed runs show DuckDB requested exactly that footer and the original guard blocked it before network access. The separate [frozen footer policy](../../research/source-publication-20261107/grwl-footer-boundary-r1/footer-policy-r1.json) permits one exact, independently hashed metadata range in the Mississippi z7 attribute case, under a 32 MiB hard ceiling. Both request and response guards enforce the exception; other requests keep the original limits. The policy does not permit column-data reads above 16 MiB or alter the dataset.

Pass this optional policy to the browser harness with `--metadata-policy PATH --metadata-policy-sha256 SHA256`, then to `validate_hosted.py` with `--browser-metadata-policy PATH --browser-metadata-policy-sha256 SHA256`. Both callers require an independent hash of the frozen file. The shared browser controls remain unchanged, and the check still requires all twenty GRWL views, fourteen source attributes and exact selected-ID equality. The hosted validator independently checks the browser report's ranges, response sizes, MIME, CORS, object identity and byte totals; it checks the footer digest against the frozen policy. These are checks of retained browser attestations, not an additional remote download. Run the focused transport checks with `node --test scripts/cloud_viewer/tests/hosted-range-policy.test.mjs` and `pytest tests/test_browser_range_evidence.py tests/test_hosted_validation.py`.

Keep every failed attempt. Correct a mistaken protocol assumption in a separate recorded addendum with primary-source support; never quietly change the acceptance rules to conceal a failure. Actual required browser preflights, ranges, visible data and feature inspection must work.

A canonical record becomes `published` only after its package identity and display pins match real passing hosted evidence. Generate the aggregate with `scripts/publication_catalog.py`, validate it with the pinned Portolan gate, and stage only the generated metadata. Test the deployed aggregate in Portolan Browser separately. Registry submission remains a separate decision.

See `research/source-publication-20261106/` for the current frozen scope, plan, controls, execution evidence and hosting decision. The portable history archive preserves earlier verification inputs; a clean repository with no historical Git objects must still reproduce the retained GEE findings before history is reset.

The official Portolan Browser also opens a Parquet preview automatically. For GRWL it reads a 512 KiB tail followed by the exact 19,259,375-byte footer prefix. The [separate official-Browser policy](../../research/source-publication-20261107/pages/five-collections-r2/footer-prefix-policy-r1.json) binds that prefix to the unchanged Source object, independent footer proof, original Browser criteria and current Pages plan. Pass `--metadata-policy PATH --metadata-policy-sha256 SHA256` to `portolan-browser-check.mjs`. It permits one exact metadata-prefix request and verifies the live body SHA-256; all other requests keep 16 MiB, with the existing 128 MiB per-collection and 640 MiB aggregate ceilings. Original failed preflight evidence is retained.

The official Browser harness captures the approved large footer prefix through a separate Chrome DevTools Network session (32 MiB per resource, 128 MiB total inspection buffer). It reads the actual browser request ID after completion; it does not refetch or replace Source responses. Request identity, status, lengths and checksum must agree with the policy and the ordinary browser evidence. This avoids the default inspector cache evicting the response before verification.
